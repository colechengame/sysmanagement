## 一、文件目的與範圍

本文件是給 **PM／需求溝通**用的後端規格版本，不涉及 Schema 型別、SQL、API Request/Response 這類工程實作細節（工程師請改看 `後端規格書.md`）。目的是讓 PM 能掌握：

1. 後端要支援哪些「模板系統參數」與「模板組合／擴充」規則
2. 預約查詢頁面的簡訊相關功能，後端要提供哪些能力
3. 後端要留存哪些操作紀錄（Log），供稽核與客服追查

### 範圍決策提醒（勿走回頭路）

跨門市瀏覽／複製模板功能已於 2026-07-02 定案移除。各門市只能讀取/管理**本門市自訂模板**與**系統內建模板**（`store_id = NULL`），資料完全隔離，不做跨店機制。詳見 [[project_npos_sms]] 範圍決策段落。

### ⚠️ 派號欄位的特別說明

原型（`prototypes/預約操作模擬.html` 內 `queueNoFromTime()`）用「預約時間 → 換算時段起點 → 每 15 分鐘遞增奇數」的公式產生 `{{派號}}`，**這套公式只是為了讓原型畫面有資料可以示意，不是後端真正規則**，開發時不需要照這個公式實作。

實際規則：**後端已完成派號功能開發**——依同一診間/時段內預約建立的**先後順序**，自動遞增產生奇數序列（1、3、5、7…），由系統自動派發，前台人員不需手動輸入號碼。

### ⚠️ 診別（早/午/晚）規則說明

「診別」跟「時段」是同一件事的兩種說法。跟派號不同，**時段判斷不需要改邏輯**——維持既有的「依預約時間換算」公式（13:00 前算早診、13:00~16:59 算午診、17:00 以後算晚診），只是這條規則之前只活在原型 JS 裡，現在需要正式落地成後端程式邏輯，讓 `{{時段}}` 參數由後端計算後回傳，不是前端自己算。

## 二、模板系統參數與組合擴充功能

### 2.1 系統參數 Token 白名單

模板 `body` 只能使用下列 token，其餘 `{{...}}` 格式一律視為不合法：

| Token | 說明 | 資料來源 |
|---|---|---|
| `{{會員姓名}}` | 會員全名 | 預約資料 |
| `{{門市名稱}}` | 門市名稱 | 門市資料 |
| `{{門市地址}}` | 完整地址 | 門市資料 |
| `{{門市電話}}` | 含區碼 | 門市資料 |
| `{{預約日期}}` | 格式 `MM/DD（星期）` | 預約資料 |
| `{{預約時間}}` | 格式 `HH:MM` | 預約資料 |
| `{{療程}}` | 施做療程項目 | 預約資料 |
| `{{診間}}` | 診療室（診一、診二…） | 預約資料 |
| `{{時段}}` | 早診／午診／晚診，由預約時間判斷 | 後端計算 |
| `{{派號}}` | 依預約建立順序自動遞增的奇數序號（見上方說明） | 後端已實作功能 |

新增模板時，若內容含有非白名單 token，後端要擋下並提示錯誤，不能存進資料庫。

**v1.2 確認**：以上 10 個 token 為最終定案清單，不會再新增「發送前才手動填寫」的參數（早期草稿曾規劃過這類欄位，已確認不需要）。另外，簡訊的「預估則數」計算規則也已定案：字數 70 字以內算 1 則，超過則每 67 字加算 1 則；這個規則同時要用在模板編輯頁的即時預覽跟後端寫入發送記錄，兩邊算出來的則數必須一致。

### 2.2 模板的兩種來源與可見性

| 來源 | 可編輯範圍 | 說明 |
|---|---|---|
| 系統內建 | 不可直接改內容 | 全系統共用；門市編輯後存檔會另存一份自訂複本，原始內建不受影響 |
| 本門市自訂 | 可編輯／刪除 | 只有建立的門市看得到、能改；其他門市看不到 |

CRUD 權限（工程細節詳見 `後端規格書.md`）：一般人員只能查看與套用；新增/編輯/刪除自訂模板需門市主管以上權限；系統內建模板只有系統管理員能調整。

### 2.3 模板組合擴充功能（套用優先序）

發送簡訊視窗開啟時，後端／前端依下列 4 條規則**由上而下依序判斷，符合就套用、不再往下**，這是「多模板」實際發揮組合效果的核心邏輯：

1. 門市有設「門市預設模板」且模板還在（未刪除/未停用）→ 套用門市預設
2. 門市完全沒有任何自訂模板 → 套用系統層級的「BU 指定模板」（目前為固定的系統内建模板，非資料庫可設定欄位）
3. 有「上次套用」紀錄且模板還在 → 套用上次模板，顯示「已沿用上次選擇」提示
4. 曾釘選過本門市自訂模板 → 套用最近釘選的自訂模板；否則 → 套用最新建立的自訂模板

**防呆要求**：門市預設或上次套用指到的模板如果已被刪除/停用，要自動退到下一層規則，不能讓畫面出錯。

未來若有更好的模板組合想推廣到全門市，做法是**擴充系統內建模板清單**（由系統/BU 端統一新增），不重啟跨門市瀏覽/複製機制。

## 三、預約查詢與簡訊相關功能

`prototypes/預約查詢互動.html` 對應的功能是預約建立後，後續「查詢/管理簡訊狀態」的主要入口，後端要支援：

| 功能 | 說明 |
|---|---|
| 查詢待發排程 | 依預約 ID 查詢該筆是否有排程中的簡訊，供前台顯示「排程中」狀態 |
| 取消排程發送（簡訊層級） | 排程中的簡訊可在發送前取消；已發送/已取消/失敗的排程不可再取消。**取消的是這筆簡訊，不是預約本身**——取消後預約仍維持原狀態（進行中），只有簡訊狀態變成「已取消」 |
| 查看簡訊詳情 | 已排程/已送達/已取消/發送失敗的預約，點擊狀態即可查看：收件人（姓名＋隱碼手機）、簡訊內容與字數、套用的模板名稱（無對應模板時顯示「自訂」）、建立時間與建立人、依狀態而定的時間或原因（排程中＝預計發送時間；已送達＝送達時間；已取消＝取消時間；發送失敗＝失敗原因）。**即使該預約診療時間已過期，只要簡訊狀態是「已送達/已取消/發送失敗」這類終態，詳情仍可唯讀點閱**（供事後查核）；「排程中」或「未發送」的過期紀錄則不可互動。**v1.2**：這支查詢已有完整的後端回應欄位契約（見 `後端規格書.md` 4.5 節），工程端可直接照著做，不需要再另外討論欄位範圍 |
| 重新發送 | 已取消或發送失敗的簡訊可重新觸發發送。**重新發送不是「原文重寄」，而是重新開啟一次完整的發送流程**——會重新跑第 2.3 節套用優先序（可能帶出不同模板）、重新判斷會員拒收／同日排程衝突情境，人員可在送出前修改內容，等同建立一筆新的發送請求 |
| 立即發送／預約發送 | 送出簡訊時可選「立即發送」或指定未來時間排程發送 |
| 同日多預約僅最早一筆可操作 | 同一會員、同一天若有多筆**未取消**的有效預約，只有時間最早的一筆會出現可互動的簡訊入口／狀態徽章；其餘同日預約的簡訊入口為唯讀鎖定狀態，不可點擊發送或查看詳情。判斷「最早」只看預約本身是否被取消，不受該筆簡訊自己的狀態（例如簡訊已被取消）影響 |
| 取消預約時的自動補位 | 若被取消的是同會員同日多筆預約中**最早**的一筆，且同日仍有其他有效預約，系統會自動導向**次早**的一筆，詢問人員是否改對這筆發送簡訊確認；人員確認送出後，原本最早那筆才正式標記為「已取消」。後端需支援「發送請求可改指定到同會員同日另一筆預約」的語意，不是單純的先取消再各自重建 |
| 重複發送防護 | 同一筆預約 5 分鐘內重複觸發發送，需擋下並提示，人員確認後才可強制重發 |
| 發送速率限制 | 單一門市每小時發送則數超過門檻需擋下，並提示可重試時間 |
| 會員拒收判斷 | 會員設定拒絕簡訊時，後端要能判斷並提示，前台人員仍可強制送出；若同時又有同日排程衝突，兩種警示會一併顯示（複合情境），仍以人員最終決定為準。**強制送出（覆蓋拒收設定）這個動作本身要能在 Log 中被追查到**，不能跟一般正常發送混在一起看不出差異 |
| 個資保護 | 手機號碼由後端依預約 ID 取得，前端不會拿到/也不會傳完整號碼；查詢/顯示一律隱碼（保留末四碼） |

## 四、操作紀錄（Log）

### 4.1 簡訊發送 Log

每一次簡訊發送（含立即發送與排程發送）都要留存紀錄，至少包含：

| 項目 | 說明 |
|---|---|
| 對應預約 | 用預約 ID 關聯，不直接存完整手機號碼 |
| 收件人（隱碼） | 僅顯示末四碼 |
| 發送內容 | 已代入參數的最終簡訊文字 |
| 簡訊則數 | 依字數換算 |
| 排程時間 | 空值代表立即發送 |
| 狀態 | 排程中／已送達／已取消／發送失敗 |
| 相關時間戳記 | 送達時間／取消時間／失敗原因發生時間 |
| 覆蓋發送標記 | 是否為「會員已設定拒收，人員強制送出」的情況；true/false，供事後追查是否有不當覆蓋 |

用途：客服查詢發送記錄、統計發送量與失敗率、稽核個資使用情形。

### 4.2 模板異動稽核 Log

模板的新增／編輯／刪除都要留稽核紀錄，至少包含：

| 項目 | 說明 |
|---|---|
| 操作者 | 是誰改的 |
| 動作 | 新增／編輯／刪除 |
| 被改的模板 | 模板 ID／名稱 |
| 異動內容 | 改之前/改之後的差異（名稱、內容、啟用狀態） |
| 操作時間 | 時間戳記 |

用途：日後追查「誰改了這條簡訊模板、什麼時候改的、改了什麼」，避免模板被誤改後找不到人負責。

兩類 Log 建議保留至少 12 個月。

## 五、驗收標準（PM／UAT 用）

- [ ] 建立自訂模板時使用白名單以外的參數 → 儲存被擋下並有錯誤提示
- [ ] 切換門市帳號登入 → 看不到其他門市的自訂模板，只看得到自己門市 + 系統內建
- [ ] 門市沒有任何自訂模板時開發送視窗 → 自動套用 BU 指定模板
- [ ] 設定門市預設後開發送視窗 → 優先套用門市預設，不受「上次套用」影響
- [ ] 門市預設模板被刪除後開發送視窗 → 不出錯，自動退到下一層規則
- [ ] 預約查詢頁可看到排程中的簡訊，並可成功取消
- [ ] 取消排程中的簡訊後，預約本身狀態不受影響（僅簡訊變為已取消，預約仍為進行中）
- [ ] 已取消/發送失敗的簡訊可重新發送成功；重新發送會重新套用優先序規則與拒收/衝突情境判斷，非原文重寄
- [ ] 同一會員同一天有多筆有效預約時，只有時間最早一筆可操作簡訊；其餘顯示唯讀且無法點擊
- [ ] 取消同會員同日最早一筆的「預約」時，系統自動導向次早一筆詢問是否發送簡訊，確認送出後原預約才轉為已取消
- [ ] 已過期但簡訊狀態為已送達/已取消/發送失敗的預約，仍可唯讀點閱簡訊詳情內容
- [ ] 同一預約 5 分鐘內重複發送 → 被擋下，需確認才可強制重發
- [ ] 會員設定拒絕簡訊時仍強制發送 → 該筆 Log 的覆蓋發送標記為 true，可被追查
- [ ] 後台可查到簡訊發送 Log，手機號碼皆為隱碼
- [ ] 後台可查到模板新增/編輯/刪除的稽核紀錄，含操作者與異動內容
- [ ] 派號欄位在簡訊內容中正確顯示為系統自動遞增的奇數序號（非原型的時間公式）
- [ ] 診別（{{時段}}）依預約時間正確判斷早/午/晚診，由後端計算，非前端自行推算
- [ ] 模板編輯頁預覽的預估則數，跟後端 `sms_send_log.segments` 寫入值，兩邊算出來的數字一致
- [ ] 查詢單筆簡訊詳情時，即使模板已被刪除（`template_name` 為 null），查詢仍正常回傳，前端顯示「自訂」
