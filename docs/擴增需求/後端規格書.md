## 一、系統參數白名單

`body` 欄位僅允許以下 token，其他 `{{...}}` 格式儲存時回 400。

| Token | 說明 | 解析來源 |
|---|---|---|
| `{{會員姓名}}` | 會員全名 | `appointments.member_name` |
| `{{門市名稱}}` | 門市名稱 | `stores.name` |
| `{{預約日期}}` | 格式 `MM/DD（星期）` | `appointments.date` |
| `{{預約時間}}` | 格式 `HH:MM` | `appointments.time` |
| `{{療程}}` | 施做療程項目 | `appointments.treatment_name` |
| `{{診間}}` | 診療室（診一、診二 …） | `appointments.room` |
| `{{時段}}` | 早診 / 午診 / 晚診（由時間推算，見第二節） | 後端計算 |
| `{{派號}}` | 依預約建立順序自動遞增之奇數序號（見第二節） | 後端計算（已實作） |
| `{{門市地址}}` | 完整地址 | `stores.address` |
| `{{門市電話}}` | 含區碼，如 `02-XXXX-XXXX` | `stores.phone` |

> **v1.7 確認**：以上 10 個 token 為最終定案清單（對照 `prototypes/模板簡訊設定教學.html` 的 `SYS` 陣列），不會再增加「手動輸入型」參數（例如早期草稿曾規劃的 `{{注意事項}}`/`{{其他備註}}`，已確認不需要，模板一律是系統參數自動帶入，沒有發送前才手填的欄位）。

## 二、時段判斷（診別）與派號規則

> 「時段判斷」與「診別」是同一件事的兩種說法（早診／午診／晚診），下同。

### 2.1 時段判斷（診別）

```
appointment.time（HH:MM）→ 換算成分鐘數 total

total < 13:00（780 分）  → 早診
total < 17:00（1020 分） → 午診
total ≥ 17:00            → 晚診
```

> **v1.7 確認**：此公式**維持不變、正式定案**，需正式落地為後端程式（先前只在 `prototypes/預約操作模擬.html`／`模板簡訊設定教學.html` 的 `shiftFromTimeStr()` 存在，未落地後端）。跟 v1.5 修正過的「派號」不同——診別／時段就是單純依預約時間的時間帶判斷，不是依建立順序或診間排班表，不需要另外設計規則。

### 2.2 派號規則（後端已實作，非時間換算）

派號**不是由預約時間換算**，而是依**同一診間／同一時段內，預約建立的先後順序**，由後端自動遞增產生奇數序號：

```
同一診間 + 同一時段內，依預約建立順序遞增：
派號 = 1 + (該診間/時段內建立順位 − 1) × 2   // 奇數序列：1、3、5、7 …
```

範例（同一診間、同一時段，依建立順序）：

| 建立順位 | 派號 |
|---|---|
| 第 1 筆 | 1 |
| 第 2 筆 | 3 |
| 第 3 筆 | 5 |
| 第 4 筆 | 7 |

> ⚠️ **修正說明（v1.5）**：v1.1～v1.4 版本曾記錄「依預約時間換算、每 15 分鐘一格」的公式，該公式僅為原型（`prototypes/預約操作模擬.html` 內 `queueNoFromTime()`）用來產生示意假資料，並非後端實際規則，已於此版修正為依建立順序遞增的實作邏輯。

### 2.3 簡訊字數與則數換算（v1.7 新增）

對照 `prototypes/模板簡訊設定教學.html` 的 `smsSegments()`，字數／則數換算公式：

```
len = 已代入所有 {{token}} 後的最終簡訊字元數（字元數，非 byte 數；中文字與半形英數字都算 1）

len === 0        → 0 則
len <= 70        → 1 則
len > 70          → ceil(len / 67) 則
```

此公式同時用於：① 模板編輯頁即時預覽的「預估簡訊則數」；② `sms_send_log.segments` 寫入值。兩處必須算法一致，避免前端預覽跟後端 Log 對不起來。

## 三之一、模板可見性與所有權 (已調整：移除跨店功能)

採「**本門市獨立運作**」設計——各門市只能查看及管理本門市與系統內建之模板，無法跨店瀏覽其他門市的模板。

| 操作 | 規則 |
| --- | --- |
| **讀取（GET）** | 僅回傳本門市與系統內建的模板，其他門市之模板不予回傳 |
| **新增（POST）** | 只能建立 `store_id = session.store_id` 的模板 |
| **編輯 / 刪除** | 只能操作 `template.store_id === session.store_id` 的模板，其他均 403 |
| **系統內建** | `store_id = NULL`，任何門市唯讀；系統管理員可改 `enabled` / `body` |

### POST `/api/sms/send` 重點欄位

```json
{
  "appointment_id": 10042,
  "template_id": "b2",
  "content": "已解析的最終文字（前端人員可能已手動修改）",
  "scheduled_at": null
}
```

- `appointment_id` → 後端自行取手機號碼，前端不傳
- `content` → 長度上限 670 字；超過回 400
- `scheduled_at` 為 null 或省略 → 立即發送

### 4.1 同日多預約：僅最早一筆可發送／取消

同一會員、同一天若有多筆**未取消**的預約，`POST /api/sms/send` 與 `DELETE /api/sms/scheduled/:log_id` 都只接受**時間最早**那一筆的 `appointment_id`；對非最早的預約呼叫這兩個端點一律回 409（`error: "not_earliest_appointment"`）。前端本身會鎖住非最早預約的操作入口，但後端仍需獨立驗證，避免繞過前端直接打 API。判斷「最早」只看該會員同日各筆預約本身是否為 `cancelled`，跟簡訊自己的狀態（例如簡訊已被取消）無關。

### 4.2 取消預約時的補位（前端協調的兩步驟，非單一端點）

若使用者要取消同會員同日多筆預約中「最早」的一筆，且同日還有其他有效預約，前端會改為對**次早**那一筆呼叫 `POST /api/sms/send` 讓人員確認發送內容；等這次發送成功建立（拿到 `log_id`）之後，前端才呼叫（既有、非本文件範圍的）預約取消 API 把原本最早那筆的 `appointment_status` 改為 `cancelled`。**後端不需要新增「轉移」端點**，只需確保「先送出新對象的簡訊、成功後才取消原預約」這個順序被遵守，避免中途失敗導致兩邊都取消或都沒發送的不一致狀態。

### 4.3 重新發送＝重新呼叫 send API，非重寄舊 log

`已取消`／`發送失敗` 的簡訊要「重新發送」時，前端會重新走一次模板套用優先序（見 `後端規格書（PM視角）.md` 2.3 節）與情境判斷（拒收／同日排程衝突），再呼叫 `POST /api/sms/send`。重新發送**不是**針對舊 `log_id` 做動作，而是對同一 `appointment_id` 建立一筆全新的 `sms_send_log` 記錄；`content`/`template_id` 很可能跟上一筆不同，後端不需要處理「沿用舊內容」的邏輯。

### 4.4 編輯系統內建模板＝建立新複本（非改內建本身）

對照 `prototypes/模板簡訊設定教學.html`：使用者在編輯器打開一筆系統內建模板（`is_builtin=true`）並按儲存時，前端會先跳確認彈窗（「將建立一份可自訂的複本，系統內建的原始模板不受影響」），確認後呼叫的是**一般的 `POST /api/sms-templates` 新增流程**，帶入內建模板目前的 `name`/`desc`/`body`/`enabled` 當初始值、`store_id=session.store_id`，建立一筆全新的自訂模板。**不需要新增「複本」專用端點或欄位**（例如 `copied_from_id`）——這份複本跟其他手動新增的自訂模板在資料庫層完全一樣，之後各自獨立編輯，不會再跟來源的系統內建模板產生關聯。

### 4.5 簡訊詳情查詢：回應欄位契約

對照 `prototypes/預約查詢互動.html` 的簡訊詳情彈窗（`viewSmsDetail()`），`GET /api/sms/logs/:log_id` 需回傳以下欄位供前端渲染：

```json
{
  "log_id": 9981,
  "appointment_id": 10042,
  "recipient_name": "王小明",
  "recipient_masked": "09xx-ooo-5678",
  "content": "已解析的最終簡訊文字",
  "char_count": 42,
  "template_name": "標準預約提醒",
  "status": "delivered",
  "created_at": "2026-10-30T11:32:00+08:00",
  "created_by": "陳醫師",
  "send_time": "2026-10-31T15:00:00+08:00",
  "sent_at": "2026-10-31T16:00:00+08:00",
  "cancelled_at": null,
  "fail_reason": null,
  "override_opt_out": false
}
```

- `template_name` 若查無對應模板（模板已刪除，或發送當下就沒有套用任何模板）回傳 `null`；前端顯示為「自訂」——**不是錯誤**，是正常情況，不要因為 `template_name=null` 就擋下查詢
- `sent_at` / `cancelled_at` / `fail_reason` 依 `status` 只會有一個非空（`scheduled` 時三者皆空，`send_time` 才是有意義的欄位；其餘狀態看對應欄位）
- 這支端點沒有「已過期不可查」的限制——只要 `log_id` 存在就能查，前端自己決定過期預約要不要顯示查詢入口（見 PM 視角文件第三節「查看簡訊詳情」規則）

## 八、授權驗證流程

### Session Claims（後端驗證所需）

每個 API 請求的 token 必須可解析出以下欄位：

| Claim | 說明 |
| --- | --- |
| `user_id` | 操作者帳號 ID |
| `store_id` | 操作者所屬門市 ID |
| `role` | `staff`（一般人員）/ `manager`（門市主管）/ `admin`（系統管理員） |

### 驗證原則

1. **不信任前端傳入的 store_id**：所有操作以 token 中的 `store_id` 為準。
2. **讀取開放、寫入限制**：
   - `GET` 類端點回傳全門市模板，不依 store_id 過濾。
   - `POST / PUT / DELETE` 類端點：驗 `template.store_id === token.store_id`，否則 403。
   - `store_id = NULL`（系統內建）：任何門市的 PUT/DELETE 均 403；只有 `role = admin` 才例外。
3. **Role 驗證在後端執行**，不依賴前端路由限制作為唯一防線。

### 範例：PUT /api/sms-templates/:id

```
1. 解析 token → 取得 user_id、store_id、role
2. 查詢 template WHERE id = :id
3. 若 template 不存在 → 404
4. 若 template.store_id ≠ token.store_id（含 NULL ≠ X）→ 403
5. 若 role < manager → 403
6. 若 template.is_builtin = true 且嘗試改 body/name → 403（admin 例外）
7. 執行更新
```

## 九、發送安全

### 重複發送防護（Dedup）

同一 `appointment_id` 在 **5 分鐘內**再次發送，回 409：

```json
{
  "error": "duplicate_send",
  "prev_log_id": 9981,
  "message": "此預約已於 5 分鐘內發送過簡訊"
}
```

若前端人員確認需要強制重發，Request Body 加 `"force": true` 即可覆蓋。

### 發送速率限制（Rate Limit）

| 範圍 | 上限 | 超過時回應 |
| --- | --- | --- |
| 單一門市 / 小時 | 200 則（建議起點，上線後依實際量調整） | 429 + `Retry-After` header |

### Gateway 降級

若 SMS Gateway 連續 3 次呼叫失敗，後端將 `status` 改為 `failed`、寫入 `error_msg`，**不拋 exception 給前端**，改回 `{ "status": "failed", "log_id": ... }`，由前端顯示錯誤提示並讓人員決定是否重試。

### 測試 / 沙箱模式

後端讀環境變數 `SMS_SANDBOX=true` 時，跳過 Gateway 實際呼叫，log 寫入 `status=sent`（mock），適用 staging / 測試環境，避免真實發送。

## 十、稽核日誌

`sms_templates` 的 CREATE / UPDATE / DELETE 操作需寫入 audit log，供日後追查「誰改了這條簡訊模板」。

| 欄位 | 型別 | 說明 |
| --- | --- | --- |
| `actor_id` | INT | 操作者 user_id |
| `action` | ENUM | `create` / `update` / `delete` |
| `target_id` | VARCHAR(36) | 被操作的 template id |
| `payload` | JSON | 變更前後 diff（含 name、body、enabled 的 before/after） |
| `created_at` | DATETIME | 操作時間 |

Log 保存期限同 `sms_send_log`：12 個月。

## 十一、錯誤碼速查

| 狀態碼 | 觸發情境 |
| --- | --- |
| 400 | 欄位格式 / 長度違規；`body` 含非白名單 token；`content` 超 670 字；會員拒絕簡訊 |
| 403 | 角色不足；嘗試寫入他門市或系統內建模板；嘗試改內建模板 `body` |
| 404 | `appointment_id` / `template_id` / `log_id` 不存在 |
| 409 | 模板名稱在同門市重複；5 分鐘 dedup 觸發；取消非 `pending` 排程；對非最早同日預約呼叫 `/api/sms/send` 或 `/api/sms/scheduled/:log_id`（`not_earliest_appointment`） |
| 422 | `scheduled_at` 為過去時間 |
| 429 | 超過門市每小時發送速率上限（附 `Retry-After` header） |
| 503 | SMS Gateway 無法連線（後端 log 寫 `failed`；Response 含 `retry_after` 建議值） |
