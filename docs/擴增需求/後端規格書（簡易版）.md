## 一、系統參數白名單

`body` 欄位僅允許以下 token，其他 `{{...}}` 格式儲存時回 400。

| Token | 說明 | 解析來源 |
|---|---|---|
| `{{會員姓名}}` | 會員全名 | `appointments.member_name` |
| `{{門市名稱}}` | 門市名稱 | `stores.name` |
| `{{預約日期}}` | 格式 `MM/DD（星期）` | `appointments.date` |
| `{{預約時間}}` | 格式 `HH:MM` | `appointments.time` |
| `{{療程}}` | 施做療程項目 | `appointments.treatment_name` |
| `{{診間}}` | 診療室（診一、診二 …） | `appointments.room` |
| `{{時段}}` | 早診 / 午診 / 晚診（由時間推算，見第二節） | 後端計算 |
| `{{派號}}` | 預估派號（由時間推算，見第二節） | 後端計算 |
| `{{門市地址}}` | 完整地址 | `stores.address` |
| `{{門市電話}}` | 含區碼，如 `02-XXXX-XXXX` | `stores.phone` |

## 二、時段與派號推算規則

> 派號僅為**預估值**，實際號碼由現場工作人員決定；後端在解析簡訊 token 時依此規則填入。

### 2.1 時段判斷

```
appointment.time（HH:MM）→ 換算成分鐘數 total

total < 13:00（780 分）  → 早診
total < 17:00（1020 分） → 午診
total ≥ 17:00            → 晚診
```

### 2.2 派號公式

各時段起點（分鐘）：

| 時段 | 起點 |
|---|---|
| 早診 | 09:30（570 分） |
| 午診 | 13:00（780 分） |
| 晚診 | 17:00（1020 分） |

```
offset = floor( (total − shiftStart) / 15 )   // 每 15 分鐘一格
派號   = 1 + offset × 2                        // 奇數序列：1、3、5 …
```

範例：

| 預約時間 | 時段 | 派號 |
|---|---|---|
| 09:30 | 早診 | 1 |
| 10:00 | 早診 | 5 |
| 13:00 | 午診 | 1 |
| 17:00 | 晚診 | 1 |
| 17:30 | 晚診 | 5 |
| 18:00 | 晚診 | 9 |
| 19:30 | 晚診 | 21 |

## 三之一、模板可見性與所有權

採「**全讀、只寫自己**」設計——所有門市可互相瀏覽模板，但每間門市只能管理自己的。

| 操作 | 規則 |
| --- | --- |
| **讀取（GET）** | 回傳所有模板（含其他門市與系統內建），Response 附 `is_mine: bool` 供前端排序 |
| **新增（POST）** | 只能建立 `store_id = session.store_id` 的模板；帶 `source_id` 時後端複製指定模板的 body 到本門市 |
| **編輯 / 刪除** | 只能操作 `template.store_id === session.store_id` 的模板，其他均 403 |
| **系統內建** | `store_id = NULL`，任何門市唯讀；系統管理員可改 `enabled` / `body` |

> 看到其他門市的模板想套用 → 點「複製到本門市」→ 前端 POST 帶 `source_id` → 後端建立副本，原版不動。

| 更新個人偏好 | PUT | `/api/user/sms-preferences` | 全員 |
| 發送簡訊 | POST | `/api/sms/send` | 全員 |
| 查詢待發排程 | GET | `/api/sms/scheduled?appointment_id=` | 全員（只回傳自己門市的） |

| 查詢發送記錄 | GET | `/api/sms/logs?appointment_id=&page=` | 門市主管↑；含隱碼手機；不含完整號碼 |
| 取得門市設定 | GET | `/api/store/settings` | 全員 |
| 更新門市設定 | PUT | `/api/store/settings` | 門市主管↑ |

### POST `/api/sms/send` 重點欄位

```json
{
  "appointment_id": 10042,
  "template_id": "b2",
  "content": "已解析的最終文字（前端人員可能已手動修改）",
  "scheduled_at": null
}
```

- `appointment_id` → 後端自行取手機號碼，前端不傳
- `content` → 長度上限 670 字；超過回 400
- `scheduled_at` 為 null 或省略 → 立即發送

| 規則 | 說明 |

## 七、輸入驗證規則

### 模板 CRUD

| 欄位 | 規則 | 錯誤 |
| --- | --- | --- |
| `name` | 1–64 字；同 `store_id` 範圍內唯一 | 空值/超長 → 400；重複 → 409 |
| `body` | 10–500 字；只允許白名單 token | 長度違規 → 400；非白名單 token → 400 |
| `enabled` | Boolean，必填（不接受 null） | → 400 |

### 發送 API

| 欄位 | 規則 | 錯誤 |
| --- | --- | --- |
| `content` | 1–670 字 | → 400 |
| `scheduled_at` | 若非 null，必須為未來時間 | → 422 |
| `appointment_id` | 必須存在於資料庫 | → 404 |

### 刪除模板前置

刪除時**不攔截**（前端對 `last_used_id` / `pinned_ids` 已有 fallback）。
但若有使用者仍引用此模板，Response 可附加 `warning` 欄位說明影響範圍：

```json
{
  "deleted": true,
  "warning": "2 位使用者的上次套用模板已重置為預設"
}
```

## 八、授權驗證流程

### Session Claims（後端驗證所需）

每個 API 請求的 token 必須可解析出以下欄位：

| Claim | 說明 |
| --- | --- |
| `user_id` | 操作者帳號 ID |
| `store_id` | 操作者所屬門市 ID |
| `role` | `staff`（一般人員）/ `manager`（門市主管）/ `admin`（系統管理員） |

### 驗證原則

1. **不信任前端傳入的 store_id**：所有操作以 token 中的 `store_id` 為準。
2. **讀取開放、寫入限制**：
   - `GET` 類端點回傳全門市模板，不依 store_id 過濾。
   - `POST / PUT / DELETE` 類端點：驗 `template.store_id === token.store_id`，否則 403。
   - `store_id = NULL`（系統內建）：任何門市的 PUT/DELETE 均 403；只有 `role = admin` 才例外。
3. **Role 驗證在後端執行**，不依賴前端路由限制作為唯一防線。

### 範例：PUT /api/sms-templates/:id

```
1. 解析 token → 取得 user_id、store_id、role
2. 查詢 template WHERE id = :id
3. 若 template 不存在 → 404
4. 若 template.store_id ≠ token.store_id（含 NULL ≠ X）→ 403
5. 若 role < manager → 403
6. 若 template.is_builtin = true 且嘗試改 body/name → 403（admin 例外）
7. 執行更新
```

## 九、發送安全

### 重複發送防護（Dedup）

同一 `appointment_id` 在 **5 分鐘內**再次發送，回 409：

```json
{
  "error": "duplicate_send",
  "prev_log_id": 9981,
  "message": "此預約已於 5 分鐘內發送過簡訊"
}
```

若前端人員確認需要強制重發，Request Body 加 `"force": true` 即可覆蓋。

### 發送速率限制（Rate Limit）

| 範圍 | 上限 | 超過時回應 |
| --- | --- | --- |
| 單一門市 / 小時 | 200 則（建議起點，上線後依實際量調整） | 429 + `Retry-After` header |

### Gateway 降級

若 SMS Gateway 連續 3 次呼叫失敗，後端將 `status` 改為 `failed`、寫入 `error_msg`，**不拋 exception 給前端**，改回 `{ "status": "failed", "log_id": ... }`，由前端顯示錯誤提示並讓人員決定是否重試。

### 測試 / 沙箱模式

後端讀環境變數 `SMS_SANDBOX=true` 時，跳過 Gateway 實際呼叫，log 寫入 `status=sent`（mock），適用 staging / 測試環境，避免真實發送。

## 十、稽核日誌

`sms_templates` 的 CREATE / UPDATE / DELETE 操作需寫入 audit log，供日後追查「誰改了這條簡訊模板」。

| 欄位 | 型別 | 說明 |
| --- | --- | --- |
| `actor_id` | INT | 操作者 user_id |
| `action` | ENUM | `create` / `update` / `delete` |
| `target_id` | VARCHAR(36) | 被操作的 template id |
| `payload` | JSON | 變更前後 diff（含 name、body、enabled 的 before/after） |
| `created_at` | DATETIME | 操作時間 |

Log 保存期限同 `sms_send_log`：12 個月。

## 十一、錯誤碼速查

| 狀態碼 | 觸發情境 |
| --- | --- |
| 400 | 欄位格式 / 長度違規；`body` 含非白名單 token；`content` 超 670 字；會員拒絕簡訊 |
| 403 | 角色不足；嘗試寫入他門市或系統內建模板；嘗試改內建模板 `body` |
| 404 | `appointment_id` / `template_id` / `log_id` 不存在 |
| 409 | 模板名稱在同門市重複；5 分鐘 dedup 觸發；取消非 `pending` 排程 |
| 422 | `scheduled_at` 為過去時間 |
| 429 | 超過門市每小時發送速率上限（附 `Retry-After` header） |
| 503 | SMS Gateway 無法連線（後端 log 寫 `failed`；Response 含 `retry_after` 建議值） |
