## 二、已確認的業務規則

### 2.1 系統參數 Token 白名單

模板 `body` 只能使用下列 token，其餘一律不合法：

| Token | 說明 | 資料來源 |
| --- | --- | --- |
| `{{門市名稱}}` | 門市名稱 | 門市資料 |
| `{{門市地址}}` | 完整地址 | 門市資料 |
| `{{門市電話}}` | 含區碼 | 門市資料 |
| `{{預約日期}}` | 格式 `MM/DD（星期）` | 預約資料 |
| `{{預約時間}}` | 格式 `HH:MM` | 預約資料 |
| `{{療程}}` | 施做療程項目 | 預約資料 |
| `{{診間}}` | 診療室（診一、診二…） | 預約資料 |
| `{{時段}}` | 早診／午診／晚診，由預約時間判斷 | 後端計算 |
| `{{派號}}` | 依預約建立順序自動遞增的奇數序號 | 後端已實作功能 |
| `{{叫號機網址}}` | 門診叫號/報到查詢用短網址，門市層級固定值 | ⚠️ 2026-07-13 新增，無對應現有 POS 欄位，儲存位置待與後端工程師確認 |

#### 2.1.1 99－虛擬會員新客資料

來源為 `99－虛擬會員` 時，預約顯示與簡訊收件資料必須取該筆預約的「新客姓名／新客電話」，不得使用虛擬會員代碼綁定的會員姓名／電話；簡訊送至新客電話。`HQ0000146` 為範例會員編號。新客姓名、電話皆必填且電話須通過手機格式驗證。

同一虛擬會員代碼可在同一天、同一門市建立多筆不同新客預約，故不套用同會員同日僅最早一筆可操作的限制。

> **派號欄位澄清**：原型（`預約操作模擬.html`、`預約查詢互動.html`）曾用「預約時間 → 換算時段起點 → 每 15 分鐘遞增奇數」的公式產生 `{{派號}}`，**這套公式只是原型示意假資料，不是後端真正規則**。實際規則：後端已完成派號功能開發——依同一診間/時段內預約建立的**先後順序**，自動遞增產生奇數序列（1、3、5、7…），由系統自動派發。

### 2.2 模板的兩種來源與可見性

| 來源 | 可編輯範圍 | 說明 |
| --- | --- | --- |
| 系統內建 | 不可直接改內容 | 全系統共用；門市編輯後存檔會另存一份自訂複本，原始內建不受影響 |
| 本門市自訂 | 可編輯／刪除 | 只有建立的門市看得到、能改；其他門市看不到 |

CRUD 權限：一般人員只能查看與套用；新增/編輯/刪除自訂模板需**門市主管以上**權限；系統內建模板只有**系統管理員**能調整。

### 2.3 套用優先序（模板組合擴充功能核心邏輯）

發送簡訊視窗開啟時，依下列規則**由上而下判斷，符合就套用、不再往下**：

1. 門市有設「門市預設模板」且模板還在（未刪除/未停用）？→ 是：**套用門市預設**
2. 門市完全沒有任何自訂模板？→ 是：**套用系統層級「BU 指定模板」**
3. 有「上次套用」紀錄且模板還在？→ 是：**套用上次模板**，顯示提示
4. 曾釘選過本門市自訂模板？→ 是：**套用最近釘選的自訂模板**；否：**套用最新建立的自訂模板**

> **防呆要求**：門市預設或上次套用指到的模板如果已被刪除/停用，要自動退到下一層規則，不能讓畫面出錯。未來若有更好的模板組合想推廣到全門市，做法是**擴充系統內建模板清單**（由系統/BU 端統一新增），不重啟跨門市瀏覽/複製機制。

### 2.4 會員拒收判斷（適用所有發送入口，非 C 頁專屬）

| 規則 | 說明 |
| --- | --- |
| 會員拒收判斷 | 會員設定拒絕簡訊時，後端要能判斷並提示，前台人員仍可強制送出；若同時有同日排程衝突，兩種警示會一併顯示，仍以人員最終決定為準 |

> 這項是全域規則，B 頁（預約操作發送）與 C 頁（預約查詢管理）都適用，不是 C 頁專屬功能，因此獨立於第三節之外。

## 三、預約查詢 C 頁相關後端功能

預約建立後，查詢/管理簡訊狀態的主要入口，後端要支援的能力：

| 功能 | 說明 |
| --- | --- |
| 查詢待發排程 | 依預約 ID 查詢該筆是否有排程中的簡訊，供前台顯示「排程中」狀態 |
| 取消排程發送（簡訊層級） | 排程中的簡訊可在發送前取消；已發送/已取消/失敗的排程不可再取消。**取消的是這筆簡訊，不是預約本身**——取消後預約仍維持原狀態，只有簡訊狀態變成「已取消」 |
| 查看簡訊詳情 | 已排程/已送達/已取消/發送失敗的預約，點擊狀態即可查看收件人（隱碼）、內容與字數、建立時間與建立人、依狀態而定的時間或原因。**不記錄/不顯示套用的模板名稱**（2026-07-13 定案取消，前後端皆不做）。**即使預約診療時間已過期，只要簡訊狀態是終態（已送達/已取消/發送失敗），詳情仍可唯讀點閱**；「排程中」或「未發送」的過期紀錄則不可互動 |
| 重新發送 | 已取消或發送失敗的簡訊可重新觸發發送。**不是「原文重寄」，而是重新開啟一次完整的發送流程**——會重新跑套用優先序（可能帶出不同模板）、重新判斷會員拒收／同日排程衝突情境，人員可在送出前修改內容 |
| 立即發送／預約發送 | 送出簡訊時可選「立即發送」或指定未來時間排程發送 |
| 同日多預約僅最早一筆可操作 | 一般會員同日多預約僅最早一筆可操作；99－虛擬會員例外，每筆新客預約皆可獨立操作與發送 |
| 取消預約時的自動補位 | 若被取消的是同會員同日多筆預約中**最早**的一筆，且同日仍有其他有效預約，系統會自動導向**次早**的一筆，詢問人員是否改對這筆發送簡訊確認；人員確認送出後，原本最早那筆才正式標記為「已取消」 |

> 會員拒收判斷適用於**所有發送入口（B、C 兩頁皆是）**，非 C 頁專屬，已移到第 2.4 節。

## 四、操作紀錄（Log）

### 4.1 簡訊發送 Log（每一次發送，含立即發送與排程發送）

| 項目 | 說明 |
| --- | --- |
| 對應預約 | 用預約 ID 關聯，不直接存完整手機號碼 |
| 收件人（隱碼） | 僅顯示末四碼 |
| 發送內容 | 已代入參數的最終簡訊文字 |
| 簡訊則數 | 依字數換算 |
| 排程時間 | 空值代表立即發送 |
| 狀態 | 排程中／已送達／已取消／發送失敗 |
| 相關時間戳記 | 送達時間／取消時間／失敗原因發生時間 |

用途：客服查詢發送記錄、統計發送量與失敗率、稽核個資使用情形。

### 4.2 模板建立/更新稽核（2026-07-28 簡化：不需要獨立異動歷史表；2026-07-29 補上軟刪除）

`sms_templates` 每一列本身就有建立人/建立時間/更新人/更新時間/狀態欄位（`creater`/`created_at`/`updater`/`updated_at`/`status`），更新時直接覆蓋，不另外維護一份記錄「誰在什麼時候把 A 改成 B」的異動歷史表。

**刪除模板＝軟刪除**：`status` 覆蓋成已刪除、`updater`/`updated_at` 一併更新，不是把這一列從表裡刪掉。這樣「發送簡訊視窗排除已刪除模板」跟「模板管理頁仍查得到被刪除的模板」才能同時成立。

用途：需要知道「這筆模板現在是誰建立的、誰最後更新的、目前狀態（含是否已刪除）」時，直接看模板本身的欄位即可，不需要查一份獨立的操作紀錄——因為每筆模板用 UUID 識別、更新即覆蓋同一列，不需要大量紀錄所有操作，但也因為是軟刪除，被刪除跟被編輯過的模板都還看得到。

這些欄位隨 `GET /api/sms-templates` 一起回傳即可，不需要獨立的查詢 API；但這個 GET 預設應該只回傳未刪除的模板（給發送流程用），模板管理頁要能額外查到已刪除的，可能需要查詢參數（例如 `include_deleted=true`），實際設計待與後端工程師確認。

> 兩類 Log 建議保留至少 **12 個月**。

## 五、驗收標準（PM／UAT 用）

- [ ] 建立自訂模板時使用白名單以外的參數 → 儲存被擋下並有錯誤提示
- [ ] 切換門市帳號登入 → 看不到其他門市的自訂模板，只看得到自己門市 + 系統內建
- [ ] 門市沒有任何自訂模板時開發送視窗 → 自動套用 BU 指定模板
- [ ] 設定門市預設後開發送視窗 → 優先套用門市預設，不受「上次套用」影響
- [ ] 門市預設模板被刪除後開發送視窗 → 不出錯，自動退到下一層規則
- [ ] 預約查詢頁可看到排程中的簡訊，並可成功取消
- [ ] 取消排程中的簡訊後，預約本身狀態不受影響（僅簡訊變為已取消，預約仍為進行中）
- [ ] 已取消/發送失敗的簡訊可重新發送成功；重新發送會重新套用優先序規則與拒收/衝突情境判斷，非原文重寄
- [ ] 一般會員同一天有多筆有效預約時，只有時間最早一筆可操作；99－虛擬會員不套用此限制
- [ ] 99－虛擬會員以新客姓名／電話顯示，簡訊送至新客電話，且允許同日同店建立多筆不同新客預約
- [ ] 取消同會員同日最早一筆的「預約」時，系統自動導向次早一筆詢問是否發送簡訊，確認送出後原預約才轉為已取消
- [ ] 已過期但簡訊狀態為已送達/已取消/發送失敗的預約，仍可唯讀點閱簡訊詳情內容
- [ ] 後台可查到簡訊發送 Log，手機號碼皆為隱碼
- [ ] 後台可查到模板新增/編輯/刪除的稽核紀錄，含操作者與異動內容
- [ ] 派號欄位在簡訊內容中正確顯示為系統自動遞增的奇數序號（非原型的時間公式）
