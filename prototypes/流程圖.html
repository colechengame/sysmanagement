模板兩種來源

看 ID 前綴就知道權限：b_ / builtin_ 系統內建／c_ 本門市自訂

🏛️
系統內建
store_id = NULL
全系統共用
其中一筆為「BU 指定模板」
🔒 不可直接改 body/name
🏪
本門市自訂
store_id = 該門市
只有自己看得到
✏️ 可編輯／刪除
編輯「系統內建」存檔 → 自動變成一份本門市自訂複本，原始內建不受影響。曾規劃過「其他門市共用模板」（跨門市瀏覽/複製），已決定移除——未來若有更好的模板組合，直接擴充系統內建模板即可，不重啟跨門市機制。

套用優先序（開啟發送簡訊視窗時）

開窗自動帶入哪一張模板：4 條規則由上而下判斷，符合就停

📬
開啟發送簡訊視窗
1
門市有設「預設模板」且模板還在？
是→
✅ 套用門市預設
否，往下一條規則判斷
2
門市是否有任何自訂模板？
沒有→
🏛️ 套用「BU 指定模板」
有自訂模板，往下一條規則判斷
3
有『上次套用』紀錄且模板還在？
是→
🔁 套用上次模板標示「已沿用上次選擇」
否（本門市第一次套用），往下一條規則判斷
4
曾釘選過本門市自訂模板？
是→
📌 套用最近釘選的自訂模板
否，最後一條規則
否→
🆕 套用最新建立的自訂模板
4 條規則由上而下依序判斷，符合就直接套用、不再往下；規則 2-4 的結果套用時不顯示特別提示標記（只有規則 3「上次套用」會標示）；「上次套用」僅在使用者主動選擇模板或實際送出時寫入，開窗自動帶入不算

14:00 預約
鎖定唯讀
🔒
17:00 預約
鎖定唯讀
同一會員、同一天有多筆未取消的預約時，只有時間最早的一筆能發送/查看簡訊，其餘鎖定唯讀（灰階、不可點擊）。判斷「最早」只看預約本身是否被取消，跟簡訊自己的狀態無關。前端鎖住操作入口，後端 API 也獨立驗證同一規則（見第 8 節）。
6

簡訊取消 vs 預約取消分流圖

兩個獨立按鈕/流程，不可合併

✉️
取消「簡訊」
只改簡訊狀態為已取消
預約本身不受影響，仍維持進行中
📅
取消「預約」
是完全獨立的另一個動作
若取消的是同日最早一筆 → 觸發第 7 節自動補位
「取消簡訊」跟「取消預約」是兩個獨立按鈕/流程，前端分開觸發、後端分開寫入，不可合併成同一個動作或同一次交易。
7

取消最早預約後自動補位圖

前端協調的兩步驟，非後端單一端點

🗑️
取消同日最早一筆「預約」
且同日還有其他有效預約
🔁
自動導向次早一筆
開發送簡訊視窗詢問確認
📤
確認送出後
原本最早那筆才正式標記「已取消」
確認送出前，原預約狀態不會提前變更；若中途取消發送視窗，原預約維持不變。後端不需要新增「轉移」端點——這是前端依序呼叫「先發送、後取消」兩支既有 API 完成的，順序由前端保證。
8

前後端責任切分圖

同一條規則，前端擋一次、後端也要獨立驗證一次

🧩 前端負責
🔌 後端負責
規則前端後端
系統內建模板不可變更 編輯內建模板時導向「另存複本」流程，不提供直接覆蓋 UI PUT /api/sms-templates/:id 若 is_builtin=true 一律 403（admin 例外）
只能改自己門市的模板 畫面只顯示本門市與系統內建模板，不提供其他門市入口 驗證 template.store_id === token.store_id，不符一律 403
刪除門市預設模板 刪除後立即清空畫面上的門市預設顯示 同一交易內清空對應設定，避免 dangling 參照
同日多預約僅最早一筆可操作 鎖住非最早預約的操作入口（灰階、不可點擊） POST /api/sms/send、DELETE /api/sms/scheduled/:log_id 對非最早筆一律 409（not_earliest_appointment）
簡訊取消 ≠ 預約取消 「取消此排程」「取消預約」為兩個獨立按鈕/流程 分開寫入：只改 sms_send_log.status，不動預約狀態欄位
取消最早預約時的自動補位 先呼叫次早那筆的發送 API 並取得確認，成功後才呼叫預約取消 API 兩支既有 API 各自獨立驗證，不提供轉移端點，順序保證由前端負責
拒收覆蓋發送需留痕 顯示拒收阻擋提示，人員可選擇 force 強制送出 override_opt_out 寫入 true，供稽核追查
手動編輯內容後切換模板 跳覆蓋確認對話框，取消則不套用 （純前端行為，後端不涉入這條 UI 規則）
前端擋得住多數誤操作，但不能取代後端驗證——凡是能被繞過前端直接打 API 的規則，後端都必須獨立驗證一次；本圖只視覺化既有已確認的規則，未新增任何後端流程、補償機制或狀態機。
