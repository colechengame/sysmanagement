預約簡訊模板：單一模板 → 多模板擴增

範圍：模板管理、預約操作發送、預約查詢管理 三個畫面　目的：對齊要完成的功能清單與資料結構，作為實作討論的共同文件

1

背景與範圍

從哪裡到哪裡

單一固定模板→ 依門市/情境可選多套模板

現況每間門市只能用同一套固定簡訊內容；擴增後每間門市可以擁有自己的自訂模板、設定門市預設，並在兩個發送簡訊的入口（預約操作、預約查詢）用同一套模板選擇器挑選要套用的模板。 這份文件涵蓋三個畫面的完整功能規格：模板管理（CRUD 的地方）、預約操作（第一個發送入口）、預約查詢（第二個發送入口，同時也是事後查閱/管理簡訊狀態的地方）。

目前這三個畫面在 prototypes/ 已有可互動的原型（模板簡訊設定教學.html／預約操作模擬.html／預約查詢互動.html），資料層用 localStorage 模擬；這份文件把原型裡已經驗證過的規則抽出來，作為正式功能規格，不是重講一次原型長怎樣。
範圍決策（已定案）：原本規劃過「其他門市共用模板」（可瀏覽/複製別門市自訂的模板），最終決定移除，聚焦在系統內建模板，讓使用者專注於門市自己的模板管理，不需要在管理頁面處理跨門市瀏覽/權限等複雜度。若未來發現有更好的模板組合值得推廣，走法是直接擴充系統內建模板清單（由系統/BU 端統一新增，讓所有門市看到新選項），而不是做跨門市瀏覽或複製機制。

3

套用優先序邏輯

發送簡訊視窗一開啟，要自動帶入哪個模板

門市預設存在且該模板還沒被刪 → 直接套用（最高優先，不變）
門市預設不存在或已被刪→ 門市是否有任何自訂模板？
有自訂模板→ 個人上次套用還存在 → 套用並標示「已沿用上次選擇」（不變）
有自訂模板，但沒有上次套用紀錄（本門市第一次套用）→ 曾釘選過本門市自訂模板？
是→ 套用最近一次釘選的自訂模板 否 → 套用最新建立的自訂模板
完全沒有任何自訂模板→ 套用「BU 指定模板」
這段判斷需要對「模板是否還存在」做防呆——門市預設或個人上次套用指到的模板可能已經被刪除，這時候要自動往下一層 fallback，不能整個畫面壞掉或跳錯誤訊息。新增的「首次套用」分支（釘選自訂／最新自訂／BU 指定）套用時不顯示特別提示標記，只有「上次套用」這一步繼續顯示「已沿用上次選擇」。
4

三個畫面的功能規格

逐頁列出要完成的功能

🛠️ A. 模板管理　CRUD 中樞

對應原型：prototypes/模板簡訊設定教學.html
  • 清單：可搜尋（比對名稱/說明），依「釘選／本門市自訂／系統內建」分組顯示，同一模板不會同時出現在兩組
  • 編輯器：模板名稱（必填）、用途說明、簡訊內容（必填，可點擊插入 {{參數}}）、即時預覽（手機訊息樣式 + 字數/簡訊則數估算）
  • 編輯規則：本門市自訂可直接改存；系統內建編輯後存檔會另存為自訂複本（不覆蓋原內建，且要有明確提示，不能靜默發生）
  • 門市預設：可設定/取消目前編輯中的模板為門市預設，會影響第 3 節的套用優先序
  • BU 指定模板：唯讀 badge，標示哪一筆是「BU 指定模板」（第 3 節的最終 fallback），沒有互動設定按鈕
  • 啟用/停用：關閉後這個模板從發送畫面的選擇器消失（釘選 chips 與自動套用也會一併跳過），但管理清單裡還看得到、還能重新啟用；系統內建模板固定為啟用，要調整請先另存自訂複本
  • 刪除：需要二次確認；如果刪的剛好是門市預設，要同時清掉預設設定，不能留下指向不存在模板的殘留設定
  • 資料保護：編輯到一半離開（切模板／新增／關頁）需要有未儲存變更的提醒，避免內容被無聲蓋掉或遺失

🧩 B. 預約操作 - 發送簡訊　第一個發送入口

對應原型：prototypes/預約操作模擬.html
  • 開啟發送簡訊視窗時，依第 3 節的優先序自動帶入一個模板並解析參數（例如把 {{會員姓名}} 換成這筆預約實際的會員姓名）
  • 模板選擇器：預設收合——多數情況店員不需要換模板，收合狀態只顯示「目前套用：模板名稱」＋來源標籤（自訂／系統預設）＋（沿用上次時的）提示＋一顆「更換」按鈕，不佔用彈窗空間；點「更換」才展開篩選框＋清單，選定後自動收回（也可手動點「收合」不選就關閉）
  • 釘選模板的快速套用 chips 全程可見，不受收合/展開影響——常用模板一鍵套用，不必展開清單；沒有釘選任何模板時這排不顯示
  • 展開的清單只放「已啟用的本門市自訂模板」與「系統預設（BU 指定模板）」，不顯示「最近使用」與其他系統內建模板；已釘選的模板不重複出現在清單裡——它們已經常駐顯示在上面的 chips，避免同一批模板在兩個地方各顯示一次
  • 套用模板＝即時把內容框換成解析過參數的文字；若使用者已手動編輯過內容才切換模板（含點擊 chips），需二次確認才覆蓋，避免無聲蓋掉手動修改的內容；「個人上次套用」只在使用者主動選擇模板或實際送出時記錄，開窗自動帶入不記錄——否則開過一次視窗就會產生紀錄，第 3 節「首次套用」的分支永遠不會觸發
  • 客戶若設定「不收簡訊」，要有明顯阻擋提示，避免店員忽略誤送

🔍 C. 預約查詢 - 簡訊管理狀態　第二個發送入口 + 事後管理

對應原型：prototypes/預約查詢互動.html
  • 套用模板的規則跟 B 完全一致（收合/展開行為、分組邏輯、優先序、參數解析、覆蓋確認都共用同一套規則，不要各自長出不同的行為）
  • 簡訊送出時要記錄本次使用的模板名稱
  • 排程詳情要能查閱：依 5 種簡訊狀態（未發送／排程中／已送達／已取消／發送失敗）顯示對應顏色的狀態列，並顯示套用的模板名稱
  • 詳情畫面依狀態提供對應操作：排程中可「取消此排程」；已取消/發送失敗可「重新發送」；已送達只能「關閉」
  • 要有連到「模板管理」的捷徑，方便店員發現目前沒有合用的模板時直接跳去建立
5

建議抽成共用邏輯的部分

B、C 兩個畫面重複用到的東西，正式實作時不建議各自複製一份

  • 模板選擇器元件：收合狀態＋展開清單＋篩選＋釘選 chips＋覆蓋確認，B、C 目前規則完全一致，建議抽成共用元件，避免兩邊各自維護、之後規則跑掉不同步
  • 套用優先序判斷（第 3 節，含「首次套用」的釘選/最新自訂分支與 BU_DESIGNATED_ID 常數）：同一段邏輯，建議抽成共用函式，不要在 B、C 各寫一份
  • 模板資料存取層：模板清單、CRUD、pins/recent/default 狀態的讀寫，A/B/C 三頁都要用到，建議統一由同一層處理（不管底層是 localStorage 還是串真正的 API）
  • 參數解析（{{token}} → 實際值）：A 的即時預覽跟 B/C 的套用邏輯都需要，規則要一致
6

待討論問題

需要跟前端工程師一起拍板的地方

  1. 資料串接方式：目前規則是以 localStorage 模擬單一裝置/門市的狀態，正式環境要串真正的後端 API 嗎？如果要，模板清單／CRUD／門市預設／個人上次套用，分別該對應哪些端點跟資料表？
  2. 「個人上次套用」要綁定什麼：目前規則是綁裝置（同一顆瀏覽器/localStorage），如果同門市有多個帳號共用同一台電腦，要不要改成綁登入帳號？
  3. BU 指定模板未來是否需要開放後台設定：目前是前端寫死的常數（BU_DESIGNATED_ID），如果之後需要每個 BU 各自指定不同模板，才需要後端加對應的設定介面與資料表
  4. 共用元件怎麼落地：第 5 節列的共用邏輯，要抽成前端共用 component/hook，還是由後端統一回傳「已經算好優先序的預設模板」，讓前端少做一層判斷？
