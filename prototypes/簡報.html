簡訊模板設定畫面 — UX 修復說明

對象檔案：prototypes/模板簡訊設定教學.html　目的：走過這次改了什麼、為什麼改、還有哪些留給下一輪討論

1

背景

怎麼挑到這個畫面的

先對整個 prototype 專案（9 個獨立 HTML 檔案）做了一輪 UI/UX review，發現跨檔案的設計不一致（配色、彈窗、無障礙）規模較大，這次先聚焦在單一畫面：簡訊模板設定——這是模板 CRUD 的核心頁面，也是問題密度最高的地方。 逐行讀過原始碼後鎖定 7 個結構性問題（會造成使用者資料遺失、操作誤解、跨頁資料不一致），加上規劃時多發現的 2 個加強項目，使用者確認全部一起修。

全部改動只動了這一個檔案，沒有動到共用的 localStorage 資料結構，跟 預約操作模擬.html 的相依（npos_tpl_custom／npos_tpl_default）維持相容。
2

修了什麼

逐項對照：問題 → 修法

A

編輯到一半切換模板，靜默遺失變更

問題編輯中只要點清單另一張卡片、「＋新增」或「清空」，內容直接被蓋掉，沒有任何提示。
修法加一顆共用確認彈窗，比對編輯器目前內容跟載入時的快照（isDirty()），有差異才跳出「捨棄目前變更？」。
B/C

刪除沒有二次確認，刪到「門市預設」會留下 stale 資料

問題按刪除立即生效；如果刪的剛好是被設成門市預設的模板，npos_tpl_default 會指向一筆已經不存在的 id。
修法刪除前先確認；若刪的是目前預設，確認訊息會先講清楚，並在 performDelete() 裡一併清掉 defaultTplId／localStorage。
D

編輯系統內建模板，存檔後靜默變成同名複本

問題只有編輯器標題文字提示「儲存將另存為自訂」，很容易被忽略，使用者以為自己在改內建模板本身。
修法存檔前明確跳出「另存為自訂複本」確認；複本名稱維持使用者輸入原樣，不自動改名（靠清單分組＋確認文字區分，不動使用者輸入）。
E

「清空」按鈕命名跟行為不符

問題點下去其實是把編輯器重置成新增狀態，不是清空/刪除目前模板。
修法改成情境式標籤：編輯既有模板時顯示「取消編輯」，已在空白新增狀態時顯示「清空表單」。
F

「啟用」開關沒說明實際影響

問題關掉某模板只讓清單卡片變半透明，不知道實際會發生什麼事。
修法開關下方常駐顯示說明文字，即時反映開/關狀態：會/不會出現在「預約操作」發送簡訊視窗裡。
G

預覽手機畫面寄件者/地址/電話寫死本店資料

問題檢視「其他門市」模板時，寄件者標籤跟 {{門市名稱}} 等 token 仍固定顯示「示範麗雅」，跟模板實際所屬門市矛盾。
修法預覽依 contextStoreName()／contextStoreAddr()／contextStorePhone() 切換情境；順便幫 e1/e2 兩筆其他門市模板補上假地址/電話，讓完整預覽對得上。
H

額外加強：唯讀模板時「啟用」開關還能點

問題檢視其他門市模板時，名稱/說明/內容都鎖了，唯獨這顆開關還能切換。
修法視覺鎖住（半透明＋不可點擊）並在 click handler 內加防呆。
I

額外加強：離開頁面沒有警示

問題前面的確認只擋得住站內切換，重新整理或關分頁還是會無聲遺失。
修法掛上 beforeunload，dirty 時交給瀏覽器原生的離開確認提示。
3

技術實作重點

給工程師快速對照 code 用

新增的共用元件

  • confirmDialog(opts, onOk) — 輕量確認彈窗，樣式移植自 預約操作模擬.html 既有的 .scrim/.modal，A/B/D 三種情境共用同一顆元件、不同文案。
  • isDirty() / snapshotEditor() — 比對編輯器目前值跟載入時快照；對「其他門市」唯讀模板永遠回傳 false。
  • performDelete(id) / doSaveAsCopy(...) — 從原本的 saveBtn/delBtn handler 拆出來，因為現在存檔／刪除都可能先經過非同步的確認彈窗 callback。

資料模型微調

  • ext 陣列（其他門市模板）新增 storeAddr / storePhone 欄位（虛構假資料，跟現有假資料風格一致）。
  • STORE_NAME / STORE_ADDR / STORE_PHONE 常數取代原本寫死在 sample 物件跟 HTML 裡的「示範麗雅」字串。
跟 預約操作模擬.html 共用的 localStorage 鍵值（npos_tpl_custom / npos_tpl_pins / npos_tpl_default）結構完全沒變，只有多了「刪除預設模板時清空 default」這個副作用，對方頁面原本就有 stale-id 的 fallback 防呆，相容沒有問題。
4

已經拍板的決策

規劃階段跟你我來回確認過，避免討論時重複繞

項目決策原因
D · 複本命名不自動改名不動使用者輸入內容，靠確認彈窗文字 + 清單分組區分原始/複本
G · 其他門市資料補上假地址/電話讓其他門市模板的完整預覽（含地址、電話 token）都對得上，不留半套
F · 說明文字呈現常駐顯示，不用 hover tooltip跟現有 .ed-ro-bar／.param-hint 視覺語言一致，也避免觸控裝置點不到 tooltip
5

驗證方式

怎麼確認這次改動沒問題

用 headless Chrome（puppeteer-core）跑過完整互動流程：切換模板、儲存、刪除、鎖定唯讀開關、預覽情境切換、beforeunload，共 22 項細部檢查全數通過，過程中 console 無任何錯誤。也截圖確認了實際畫面（確認彈窗、其他門市預覽鎖定狀態）跟既有設計語言一致。

程式碼已經 commit（6748c04）並推送到 origin/master。
6

待討論 — 還沒動的部分

第一輪全站 review 找到、但這次刻意先不做的項目，適合這次一起排優先序

範疇問題摘要狀態
跨檔案9 個 prototype 各自手刻 CSS，沒有共用 tokens/components，配色（紫色漸層 vs NPOS 藍 vs 一般藍）三套並存未排
跨檔案不少可點擊元素是 <span>/<div onclick>，缺 role="button"/鍵盤操作，僅 index.html 側欄做對未排
跨檔案4 個教學素材（基礎.html／簡訊設定教學動畫／發送時間互動示意／優化.html）重複教同一套 SMS 流程，顏色圖例互不一致未排
單檔（預約查詢互動.html）CSS class 重複定義 bug、alert() 混用、發送無過場動畫、無 RWD、時間寫死、取消簡訊/取消預約易誤觸未排
本畫面（模板簡訊設定）7＋2 項本次已全數修復已完成
建議討論重點：要不要先做「共用 CSS tokens」這個結構性項目——影響範圍最大，但一次能解決 3 套配色系統並存的問題，後續每個畫面的維護成本都會降低。
