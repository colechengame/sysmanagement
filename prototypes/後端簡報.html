討論用簡報 · 給後端工程師

預約簡訊模板：單一模板 → 多模板擴增（後端規格）

對應前端功能規格：prototypes/簡報.html　目的：資料表設計、API 端點、需要後端把關的業務邏輯

1

背景與範圍

跟前端規格是同一件事的兩面

前端那份規格（prototypes/簡報.html）已經定義了三個畫面（模板管理／預約操作發送／預約查詢管理）要做的功能、模板的三種來源（系統內建／本門市自訂／其他門市唯讀）、套用優先序邏輯。 目前 prototype 全部用 localStorage 模擬資料層，這份文件要討論的是：正式串接後端時，這些資料該長在哪張表、要開哪些 API、有哪些規則不能只靠前端擋，後端必須驗證。

重點提醒：前端 prototype 裡「系統內建不可編輯」「刪除門市預設要連動清空」「其他門市唯讀」這些規則目前都只在前端 JS 裡擋。正式環境這些規則必須在後端也驗證一次，否則繞過前端直接打 API 就能破壞資料完整性。
2

資料表設計（建議）

把 localStorage 的鍵值換成正式資料表

sms_templates — 模板本體

欄位型別說明
idPK模板 id
store_idFK，nullablenull＝系統內建；有值＝該門市自訂／該門市擁有的模板
namestring模板名稱
descriptionstring, nullable用途說明
bodytext簡訊內容（含 {{token}}）
enabledbool停用後不進發送用清單，管理清單仍看得到
is_builtinbool與 store_id is null 等價，但獨立欄位讓查詢/權限判斷更明確
created_by / created_at / updated_at稽核用

store_template_settings — 門市層級狀態

欄位型別說明
store_idPK/FK門市
default_template_idFK，nullable門市預設模板；模板被刪除時要連動設回 null
「BU 指定模板」（門市完全沒有自訂模板時的最終 fallback）本階段沒有對應的資料表欄位——前端寫死一個常數 id（例如固定指向某筆系統內建模板），不需要後端參與。若未來要開放各 BU 各自設定，才需要新增一張 bu_template_settings 之類的表。

store_template_pins — 釘選

欄位型別說明
store_idFK門市
template_idFK被釘選的模板；模板刪除時要連動移除對應列
pinned_attimestamp排序用（新釘選排前面）

template_usage_log — 「最近使用」／「個人上次套用」

欄位型別說明
store_idFK門市
user_idFK，待討論目前 prototype 是綁裝置，正式環境建議綁登入帳號，見第 5 節
template_idFK套用的模板
used_attimestamp取最新 N 筆＝最近使用；單筆最新＝個人上次套用

appointment_sms_log — 每筆簡訊發送記錄（擴充既有預約簡訊資料）

欄位型別說明
appointment_idFK對應預約
template_idFK，nullable套用的模板；可為 null（模板之後被刪除也不影響已發送記錄）
template_name_snapshotstring發送當下的模板名稱快照，不要用 join 現查（模板改名/被刪都不能影響歷史記錄顯示）
sent_contenttext實際送出的內容
statusenumscheduled／delivered／cancelled／failed
send_timetimestamp排定發送時間
sent_at / cancelled_at / fail_reason依狀態補值
created_byFK建立排程的員工
關鍵設計：appointment_sms_log 存的是快照（模板名稱、送出內容），不是外鍵 join 現查。這樣模板被刪除、改名、停用都不會讓歷史發送記錄「壞掉」或顯示錯誤。（先前規劃的「套用後是否手動修改」追蹤欄位已確認不需要，故不再保留 applied_content_snapshot/is_modified。）
3

API 端點（建議）

對應前端三個畫面會打的請求

GET/stores/:storeId/templates
回傳該門市可用的完整清單（系統內建 + 本門市自訂 + 其他門市唯讀），後端依規則決定「其他門市」的可見範圍（見第 5 節待討論），前端只負責分組顯示、不做權限判斷。「其他門市」正式環境資料量會很大，建議加上 ?q= 搜尋參數，沒有 q 時後端可以不回傳這個分組的項目（呼應前端「其他門市預設不展開、需搜尋才顯示」的行為），避免每次都撈一份很大的清單
POST/stores/:storeId/templates
新增本門市自訂模板
PUT/templates/:id
編輯模板。後端必須驗證：若目標是系統內建（is_builtin）或不屬於這個門市，一律拒絕直接覆蓋，前端要另外呼叫「另存複本」的建立端點
DELETE/templates/:id
刪除本門市自訂模板。後端需要在同一個交易內：① 若是門市預設，同步清空 store_template_settings.default_template_id；② 清掉 store_template_pins 對應列；③ 不動 appointment_sms_log 裡的快照記錄（快照不依賴外鍵存在）
PATCH/templates/:id/enabled
切換啟用/停用
POST/templates/:id/copy
把其他門市的唯讀模板複製成本門市的自訂模板（新建一筆 store_id＝本店、內容複製過去的新紀錄）
PATCH/stores/:storeId/default-template
設定/取消門市預設模板
GET/stores/:storeId/templates/suggested?userId=
建議把套用優先序邏輯搬到後端算好直接回傳：門市預設 →（門市有自訂模板：個人上次套用 → 首次套用時改用最近釘選的自訂模板 → 否則最新建立的自訂模板）→（門市完全沒有自訂模板：BU 指定模板 BU_DESIGNATED_ID）。前端 B、C 兩個畫面都呼叫同一支，不用各自實作、也不用擔心兩邊 fallback 邏輯跑不同步
POST/appointments/:id/sms
建立發送排程：寫入 appointment_sms_log（含快照內容），並觸發實際簡訊發送（走簡訊閘道）
PATCH/appointments/:id/sms/cancel
取消排程中的簡訊
POST/appointments/:id/sms/resend
針對已取消/發送失敗的記錄重新排程發送
POST/webhooks/sms-gateway
待討論 簡訊閘道回傳實際送達/失敗結果，非同步更新 appointment_sms_log.status，取代目前 prototype 用 setTimeout 模擬 8 秒後隨機成功/失敗的作法
4

後端必須把關的業務規則

不能只靠前端擋，避免繞過 UI 直接打 API 破壞資料

  • 系統內建模板不可變更：PUT /templates/:id 若目標 is_builtin=true 一律回 4xx，前端邏輯繞過去也擋得住
  • 只能改自己門市的模板：store_id 跟登入者所屬門市不符，一律拒絕，避免 A 門市改到 B 門市的自訂模板
  • 刪除的原子性：刪模板、清門市預設、清釘選要在同一個交易內完成，避免刪到一半留下 dangling 的 default_template_id
  • 歷史記錄不可變：appointment_sms_log 一旦寫入（尤其 sent_at 之後）不應該再被模板的後續變更影響，靠快照欄位而非外鍵 join 保證這件事
  • 其他門市可見範圍：GET /stores/:storeId/templates 回傳「其他門市」清單時，範圍規則要在後端算，不能讓前端自己決定要不要顯示某門市的模板
5

待討論問題

需要跟後端工程師一起拍板的地方

  1. 其他門市可見範圍：GET /stores/:storeId/templates 裡「其他門市」清單，是全集團互相可見，還是要總部審核/白名單機制？這會決定 sms_templates 要不要多一張可見範圍的關聯表
  2. 「個人上次套用」要綁什麼：template_usage_log.user_id 綁登入帳號，還是像現在 prototype 一樣綁裝置？如果同門市多人共用一台電腦，帳號制才有意義，但要確認登入系統能不能穩定拿到 user id
  3. 簡訊閘道回傳機制：/webhooks/sms-gateway 的回傳格式、重試/逾時怎麼判定失敗、要不要有補發機制
  4. 模板變更是否需要版本歷史/稽核：醫美診所的簡訊內容可能涉及法規遵循，模板每次修改是否需要留存完整歷史（誰在何時改了什麼），而不只是 updated_at 一個時間戳
  5. 套用優先序邏輯放哪：第 3 節建議搬到後端的 GET .../templates/suggested，需要跟前端工程師確認要不要這樣切，還是維持前端各自判斷（目前兩邊各有一份重複邏輯，容易跑不同步）
