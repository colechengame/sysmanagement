後端負責範圍

跟前端規格是同一件事的兩面

⚠️ 本文件第 3、4 節所有資料表／API 皆為建議設計，非最終 schema，尚未與後端工程師逐項核對，也沒有對照過公司既有 POS 架構

前端規格（prototypes/前端簡報.html）已定義三個畫面（模板管理／預約操作發送／預約查詢管理）要做的功能、模板的兩種來源、套用優先序邏輯。 後端要負責的是：資料表設計、API 端點、以及哪些規則不能只靠前端擋、後端必須獨立驗證一次。

「模板」整套系統在公司既有 POS 架構裡完全沒有對應資料表，是全新設計。依 後端規格書.md v1.7：sms_templates／appointments／stores／sms_send_log 等都是示意用資料表，實際串接時需對照 docs/pos_schema_exports/ 的真實 schema 重新評估欄位/型別/命名，不是已拍板的契約。
跨門市共用模板功能已定案移除：各門市只能讀取/管理本門市自訂模板與系統內建模板（store_id = NULL），資料完全隔離，本文件不包含跨店瀏覽/複製的資料表或 API 設計。
2

已確認的業務規則

依 後端規格書.md 已定案/已實作的規則，非待討論項目

  • 模板可見性隔離：各門市只能讀取/管理本門市自訂模板（store_id 相符）與系統內建模板（store_id = NULL）；寫入類操作驗證 template.store_id === token.store_id，不符一律 403
  • 系統內建模板不可變更 body/name：僅 role = admin 可調整 enabled；一般門市編輯後存檔會另存為自訂複本
  • 時段判斷公式（早診 <13:00／午診 <17:00／晚診 ≥17:00）：維持既有公式不變，只是需要正式落地成後端程式（先前只在原型 JS）
  • 派號規則（後端已實作）：不是依預約時間換算，而是依同一診間/同一時段內，預約建立的先後順序，遞增產生奇數序號（1、3、5、7…）
  • 同日多預約僅最早一筆可發送/取消（後端已實作）：同一會員同一天有多筆未取消預約時，發送與取消排程 API 只接受時間最早那筆的 appointment_id，判斷「最早」只看預約本身是否 cancelled，跟簡訊自己的狀態無關
  • 簡訊取消 ≠ 預約取消：取消排程只改 sms_send_log.status，預約本身的狀態欄位不受影響，兩者是獨立寫入
  • 重新發送＝重新呼叫發送 API：不是針對舊 log 重寄，而是對同一 appointment_id 建立一筆全新 sms_send_log，內容可能因套用優先序/情境判斷不同而跟上一筆不同
  • 拒收覆蓋發送需留痕：會員拒絕簡訊、人員仍強制送出時，sms_send_log.override_opt_out 需寫 true
  • 個資保護：手機號碼由後端從 appointment_id 關聯取得，不接受前端傳入完整號碼；Log 僅存隱碼末四碼，API Response 不回傳完整號碼
  • 發送安全：同一 appointment_id 5 分鐘內重複發送需擋下（可 force:true 覆蓋）；單一門市每小時發送則數有上限（起始值可調整 目前建議 200 則，見第 8 節）

建議資料模型，非最終 schema

資料表名稱/欄位取自 後端規格書.md 三、資料模型，供工程核對用

⚠️ 以下欄位為建議設計，需與後端工程師依真實 POS schema 核對，不代表最終契約（詳見第 7 節）

sms_templates — 模板本體

欄位型別說明
idVARCHAR(36) PK系統內建前綴 builtin_，自訂前綴 c_
store_idINT FK，nullableNULL＝全系統共用
nameVARCHAR(64)同門市範圍唯一
bodyTEXT含 {{Token}} 的模板內容
enabledBOOLEANfalse 時不出現在前端下拉
is_builtinBOOLEANtrue 時不可刪除、不可改 body

sms_user_preferences — 個人偏好（釘選／最近使用／上次套用）

欄位型別說明
user_idINT PK綁登入帳號，非裝置
pinned_idsJSON Array釘選模板 ID
recent_idsJSON Array最近使用（上限 5）
last_used_idVARCHAR(36)上次套用的模板 ID

sms_store_settings — 門市層級設定

欄位型別說明
store_idINT PK
sms_enabledBOOLEAN全域發送開關
include_teleBOOLEAN包含電訪推廣附加語
「門市預設模板」「BU 指定模板」欄位目前不在 後端規格書.md 既有資料表清單裡明確列出獨立欄位；BU 指定模板本階段為前端寫死常數，非資料庫欄位。若門市預設要落地成資料表欄位，需與後端工程師另行核對放在哪張表。

sms_send_log — 每筆簡訊發送記錄

欄位型別說明
appointment_idINT FK用於查手機號碼，不直接儲存完整號碼
recipient_maskedVARCHAR(20)隱碼：09xx-ooo-NNNN（僅末四碼）
contentTEXT已解析的最終簡訊文字
segmentsINT簡訊則數
scheduled_atDATETIMENULL＝立即發送
statusENUMpending / sent / failed
override_opt_outBOOLEAN會員已拒收、人員仍強制送出；預設 false，供稽核追查

稽核日誌（模板 CREATE/UPDATE/DELETE）

欄位型別說明
actor_idINT操作者 user_id
actionENUMcreate / update / delete
target_idVARCHAR(36)被操作的 template id
payloadJSON變更前後 diff（name／body／enabled）
created_atDATETIME操作時間
兩類 Log（發送 Log、模板稽核 Log）建議保留至少 12 個月。
4

建議 API 分層

取自 後端規格書.md 四、API 端點速查，同樣為建議設計

GET/api/sms-templates
取得本門市與系統內建模板清單（全員權限）。只回傳本門市＋系統內建，不可回傳其他門市自訂模板（跨店功能已移除）
POST/api/sms-templates
新增自訂模板（門市主管以上）
PUT/api/sms-templates/:id
更新模板（門市主管以上）；只能改自己門市的；系統內建僅可改 enabled
DELETE/api/sms-templates/:id
刪除自訂模板（門市主管以上）；只能刪自己門市的，內建不可刪
GET/api/user/sms-preferences / PUT/api/user/sms-preferences
取得/更新個人偏好（釘選、上次套用等），全員權限
POST/api/sms/send
發送簡訊（全員）。Body：appointment_id、template_id、content（前端可能已手動修改，長度上限 670 字）、scheduled_at（null＝立即發送）。appointment_id 後端自行取手機號碼，前端不傳
GET/api/sms/scheduled?appointment_id=
查詢待發排程（全員，只回傳自己門市的）
DELETE/api/sms/scheduled/:log_id
取消排程發送（全員）；status 必須為 pending，否則 409
GET/api/sms/logs?appointment_id=&page=
查詢發送記錄（門市主管以上）；含隱碼手機，不含完整號碼
GET/api/store/settings / PUT/api/store/settings
取得/更新門市設定（PUT 需門市主管以上）
錯誤碼速查（節錄）：400 欄位格式/長度違規、非白名單 token、內容超 670 字、會員拒收；403 角色不足或寫入他門市/系統內建模板；404 id 不存在；409 模板名稱重複、5 分鐘 dedup、取消非 pending 排程、not_earliest_appointment；422 scheduled_at 為過去時間；429 超速率上限；503 Gateway 無法連線。完整版見 後端規格書.md 十一、錯誤碼速查。
5

預約查詢 C 頁相關後端注意事項

依 後端規格書（PM視角）.md 三、預約查詢與簡訊相關功能

  • 查詢待發排程：依預約 ID 查詢是否有排程中的簡訊，供前台顯示「排程中」狀態
  • 查看簡訊詳情：需回傳收件人（姓名＋隱碼手機）、簡訊內容與字數、套用的模板名稱（無對應模板顯示「自訂」）、建立時間與建立人、依狀態而定的時間或原因；即使預約診療時間已過期，只要簡訊狀態是終態（已送達/已取消/發送失敗）仍可唯讀點閱，「排程中」或「未發送」的過期紀錄則不可互動
  • 重新發送：語意上等同重新呼叫一次 POST /api/sms/send，會重新跑套用優先序與拒收/同日排程衝突判斷，人員可在送出前修改內容；後端應建立全新記錄，不是修改舊那筆
  • 立即發送／預約發送：scheduled_at 為 null 或省略＝立即發送，非 null 需為未來時間（否則 422）
  • 會員拒收判斷：後端判斷拒絕狀態並回 400；前端可加 "force": true 強制送出，此時 override_opt_out 需寫 true
  • 個資保護：手機號碼由後端依 appointment_id 取得，查詢/顯示一律隱碼
同日多預約僅最早一筆可操作、簡訊取消≠預約取消、取消最早預約自動補位——這三條規則的資料一致性風險獨立整理在第 6 節。
6

簡訊取消／預約取消／自動補位資料一致性風險

後端必須把關，不能只靠前端擋

  • 同日多預約僅最早一筆可操作（後端已實作）：POST /api/sms/send、DELETE /api/sms/scheduled/:log_id 只接受最早那筆的 appointment_id，其餘一律回 409（not_earliest_appointment）。前端雖已鎖住其他預約的操作入口，後端仍需獨立驗證，避免繞過前端直接打 API 破壞規則
  • 簡訊取消不等於預約取消：DELETE /api/sms/scheduled/:log_id 只改 sms_send_log.status，預約本身的狀態欄位不受影響——這是兩個獨立寫入，不要合併成同一次交易
  • 取消最早預約時的補位順序（前端協調兩步驟，非單一端點）：使用者取消同會員同日最早一筆「預約」且同日仍有其他有效預約時，前端會先對次早那筆呼叫 POST /api/sms/send，等這筆成功建立（拿到 log_id）後，前端才呼叫（既有、非本文件範圍的）預約取消 API 把原本最早那筆標記為 cancelled。後端不需要新增「轉移」端點，但要留意這個順序是前端負責協調的兩次獨立呼叫——若前端在兩步驟之間失敗（例如送出成功但取消 API 逾時），可能造成「兩筆都有效」的暫時不一致狀態，這是現有設計已知的風險點，本文件不新增補償機制，如需處理需另外討論
  • 重新發送需建立全新記錄：不可對舊 log_id 做更新，否則會讓「重新發送」跟「原始發送」的歷史記錄互相覆蓋，影響稽核追溯

後端需核對 POS 既有架構的項目

依 後端規格書.md v1.7 修改紀錄；不可自行延伸欄位或結論

本節僅引用 後端規格書.md v1.7 已明文記載的內容，不自行延伸欄位或結論。
  • 本文件第 3、4 節的 sms_templates／appointments／stores／sms_send_log 等皆為示意用資料表，實際串接時請對照公司既有 POS 架構（docs/pos_schema_exports/）
